The Channel Reader connector

A Channel Reader is a source connector that only receives messages from inside the same OIE server. It doesn't listen on a network port or poll a folder; messages reach it from another channel. Think of it as the "inbox" of a channel that other channels deliver to.

Where its messages come from

SenderHow
Another channel's Channel Writer destinationThe usual way: the destination points at this channel
A JavaScript step or script in another channelrouter.routeMessage('Channel name', msg) or router.routeMessageByChannelId(id, msg)
You, by handSend Message on the Dashboard or in the Message Browser, as in Lab 3

Settings

The Channel Reader has no settings of its own. Only the standard source settings apply:

  • Response: what the reader returns to the sender, for example None, an auto-generated ACK, or a destination's response. The Channel Writer that sent the message receives this as its response.
  • Source queue: off means the sender waits until this channel has processed the message. On means the sender continues straight away and this channel works through its queue.
  • Process batch and max processing threads: the same as on other source connectors.

Its partner: the Channel Writer

The Channel Writer is the destination that sends to a Channel Reader. You set:

  • Channel Id: the target channel. None means the message goes nowhere, which is what Lab 3 uses so you can test without a second channel.
  • Template: what is sent. The default ${message.encodedData} is the message as this destination encoded it.
  • Map variables: values from the sender's maps that are copied into the receiver's source map. OIE also adds sourceChannelId and sourceMessageId automatically, so the receiving channel can see where a message came from.

Why use it

The typical pattern is one inbound channel that routes to several processing channels:

                          ┌─ Channel Writer → [ADT to LIS]    (Channel Reader)
[HL7 in] (TCP/MLLP) ──────┼─ Channel Writer → [ADT to PACS]   (Channel Reader)
                          └─ Channel Writer → [ADT archive]   (Channel Reader)
  • One connection to the sending system: only one channel listens on a port, so you don't need a separate interface per receiving system.
  • Small channels: each channel does one job, which makes it easier to understand, test and change.
  • Independent changes: you can change, stop or redeploy one target without touching the others.
  • Easy testing: with Send Message you can test a channel directly, without a sending system.

Common pitfalls

  • The target must be deployed. If the receiving channel is undeployed or stopped, the Channel Writer's message fails with an error.
  • Data types must match. The receiver's inbound data type must match what the writer sends. For example, don't send XML into a channel that expects HL7 v2.
  • Avoid loops. A channel that writes to itself, or two channels that write to each other, keeps sending the same message forever.
  • Waiting takes time. With the source queue off, every Channel Writer waits for the downstream channel to finish processing. In long chains, turn on a destination queue or the source queue.
