The Channel Writer connector

A Channel Writer is a destination connector that sends a message to another channel on the same OIE server. It doesn't open a network connection or write a file; it hands the message straight to a channel whose source is a Channel Reader. Think of it as the "outbox" that delivers to another channel's inbox.

Settings

SettingWhat it does
Channel IdThe channel that receives the message. Its source must be a Channel Reader. None means the message goes nowhere, which is what Lab 3 uses so you can test without a second channel.
TemplateWhat is sent. The default ${message.encodedData} is the message after this destination's transformer. Use ${message.rawData} to forward the original message unchanged.
Map VariablesNames of variables to pass along. OIE looks each name up in this channel's maps and copies the value into the receiving channel's source map.

The standard destination settings also apply, such as queuing, retry count and retry interval.

What the receiving channel gets

  • The message, as built by the Template.
  • In its source map: the variables from Map Variables, plus sourceChannelId and sourceMessageId, which OIE adds automatically. Use them to find out where a message came from.

The response

The Channel Writer gets the receiving channel's response back, as set in that channel's Channel Reader under Response (for example None, an auto-generated ACK, or a destination's response). If the receiving channel's source queue is off, the Channel Writer waits until the message has been processed there.

When to use it

The typical pattern is one inbound channel that routes to several processing channels:

                          ┌─ Channel Writer → [ADT to LIS]    (Channel Reader)
[HL7 in] (TCP/MLLP) ──────┼─ Channel Writer → [ADT to PACS]   (Channel Reader)
                          └─ Channel Writer → [ADT archive]   (Channel Reader)
  • Fan out: one message from a sending system goes to several receiving channels, one Channel Writer each.
  • Split the work: clean up or convert a message once, then pass it on to channels that each do one job.
  • Reuse: several channels can send to one shared channel, for example for archiving or error notification.

Common pitfalls

  • The target must be deployed. If the receiving channel is undeployed or stopped, the message gets status ERROR. Turn on the destination queue to keep the message and retry it later instead.
  • Encoded or raw? ${message.encodedData} sends the result of this destination's transformer. If the receiver expects the original message, use ${message.rawData}.
  • Data types must match. This destination's outbound data type should match the receiving channel's inbound data type. For example, don't send XML into a channel that expects HL7 v2.
  • Avoid loops. A channel that writes to itself, or two channels that write to each other, keeps sending the same message forever.
  • Pick the channel, not the name. The Channel Writer stores the channel's ID. Renaming the target is fine, but if you delete it and import it again with a new ID, update the Channel Writer.
